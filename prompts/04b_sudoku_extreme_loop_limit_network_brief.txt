## Your task

Write the weights of a looped transformer that solves Sudoku puzzles from Sudoku-Extreme. Nothing is trained: every
weight is written by code you write.

**Loop limit: R is at most 1,000.** R is the number of times the block runs (the frame below), and it must be at most
1,000 on every prompt. `tools/dev_run.py` refuses a network over the limit, and the orchestrator checks it when it
freezes your files; a network over the limit is not run on TEST.

**Sudoku.** A puzzle is a 9 × 9 grid divided into nine 3 × 3 boxes. Some cells are given a digit from 1 to 9; the rest
are empty.
- A solution fills every empty cell with a digit from 1 to 9, so that every row, every column and every box contains
  each of the digits 1 to 9 exactly once.
- The given digits stay as they are.
- Every puzzle here has exactly one solution.

**Input.** Each problem is one text prompt, exactly as a language model receives it:

```
Solve this Sudoku:
<row 1>
...
<row 9>
```

Each row is 9 characters: a digit 1–9 for a given cell, `0` for an empty cell. The rows are joined by single newlines,
and there is no newline after the last row. Every prompt is 108 characters.

**Output.** The completed grid: 9 lines of 9 digits, one row per line, digits only, with no spaces or other characters.

**Scoring:** per puzzle, solved or not (`tools/grader.py`).
- Leading and trailing newlines are removed, and lines starting with three backticks are dropped.
- Each remaining line is stripped of spaces, and the lines are joined.
- The result must equal the solution's 81 digits in row order. Anything else scores 0.
- The TEST score is the fraction of puzzles solved.

**TEST** is puzzles from Sudoku-Extreme's test file, in a fixed order. They are of the same kind as DEV. You never see
TEST. When you say you are done, the orchestrator freezes your files and runs TEST, on the GPU path (`torch32`).

## Data in your folder

- `dev/train_1000.jsonl`: 1,000 puzzles from Sudoku-Extreme's training file. Each line is `{"id", "prompt", "answer"}`,
  where `answer` is the solution's 81 digits in row order.

You may analyse the DEV inputs and answers with any code you like, as often as you like.

## The frame (fixed; implemented in `runner/`, described in `runner/README.md`)

Inference is the generic loop: embed → the same block R times → readout.

- **Input.** The network reads exactly the prompt text, character for character. Nothing is removed, added or
  reformatted.
- **Tokenizer.** You write it in `tokenizer.py` and declare it. It maps a text string to a sequence of tokens, each a
  tuple of non-negative integer fields, each below the size of its embedding table.
  - It must work unchanged on any text.
  - It must know nothing about Sudoku, grids, rows, columns, boxes or the question format.
  - The auditor checks both.
- **Embedding.** The sum of one table per token field.
- **Block.** A fixed list of layers, the same in every loop. Each layer does
  `h ← h + Σ_heads softmax(Q Kᵀ/√d_k + mask) V W_O`, then `h ← h + W2 ReLU(W1 h + b1) + b2`.
  - The mask is none or causal, per head.
  - There is no normalisation.
  - The widths and the numbers of layers and heads are yours to choose.
- **Loops.** R comes from a rule you declare that depends only on the number of tokens n (see `runner/README.md`).
  It must be at most 1,000 on every prompt (the loop limit above).
- **Readout.** A linear map at every position, then argmax over an output alphabet you declare: a list of strings,
  one of which is the empty string.
  - Each position writes one alphabet string, or nothing (the empty string).
  - The answer is the written strings in position order.
  - The harness passes that string to the grader unchanged, with nothing added. Your network must write everything
    the grader needs.
- **Arithmetic.** The runner has these paths (`runner/README.md`):
  - on a CPU, `numpy` (float64) and `numpy32` (float32, following the GPU path as closely as numpy can);
  - on the GPU, `torch32` (float32, fused attention, TF32 off).

  DEV runs on a CPU use `numpy` or `numpy32`, as you choose. DEV runs on the GPU and TEST use `torch32`. The
  written answer must be the same on `numpy` and `torch32`.
- **Compute limit.** At most 1 × 10¹⁴ FLOPs per prompt, counted by the runner from your shapes before it runs
  (`runner/flops.py`). The runner refuses any prompt over the limit. Peak GPU memory must stay under 30 GB on one
  32 GB GPU.

## Rules

1. No training, gradients or fitting weights to data. Every weight is written by your code.
2. Inference is the generic loop above, with no task logic in Python, the tokenizer or the readout. Python only
   tokenizes, runs embed → block R times → readout, and joins the written strings. The tokenizer is generic and
   declared.
3. **DEV budget: 20 runs.** A run is any evaluation of your network on official DEV problems, on any number of them.
   - Running your network on anything built from a DEV problem (a part of one, an edited copy, its grid or its answer)
     also counts as a DEV run.
   - Runs on inputs you make yourself do not count. Such inputs may reuse the prompt format, but no grid or answer
     from the DEV file.
   - Run your network on DEV, or on inputs built from DEV, only through `tools/dev_run.py` (`--from-dev` for inputs
     built from DEV), which counts each run in `ledger/`. Do not edit the ledger; the auditor checks it against your
     transcript.
4. **Where runs happen.** This machine has no GPU. `tools/dev_run.py` sends every call to the orchestrator's server
   and runs it there with this folder's `runner/`, unchanged: `numpy` and `numpy32` on its CPUs, `torch32` on its GPU
   (`--backend torch32`). Only the network and the prompts are sent; scoring, the budget and the ledger stay here.
   - A GPU run holds at most 2 × 10¹⁵ FLOPs counted over all its prompts (for example 20 puzzles at the cap).
   - Each GPU run counts as one of the 20, on DEV or on your own inputs.

   You have no cluster access yourself.
5. **Time limit:** 12 hours of working time. Time paused by a usage limit doesn't count, and the orchestrator logs each
   pause.
6. TEST is never shown to you. Do not look for it or for any other copy of Sudoku-Extreme.
7. **Isolation.**
   - Work only inside this folder: do not read, list or look through anything outside it.
   - No web or network access of any kind: no web queries, no page fetches, no `curl`, `wget`, `pip`, `ssh`, `git`
     remotes, Hugging Face or GitHub.
   - Some of this is blocked by your permissions. The rest is a rule, and your transcript is checked afterwards.
8. During the build you will receive only: "continue", how much DEV budget is left, and answers to questions about
   these rules. Design questions get "that's your call."
9. If you find a problem with the rules, the data or the frame, stop and say so rather than working around it.

- `tools/`:
  - `grader.py`: the scoring above.

- `bridge/`: the calls `tools/dev_run.py` sends to the server, written by the tool.
- `work/`: yours.

Python 3.13 with numpy is installed.
